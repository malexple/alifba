# А. Инструментарий

**1. Какой ассемблер используем?**

**Однозначно FASM (Flat Assembler).**

- **Почему не TASM/MASM:** Старые ассемблеры требуют громоздкой настройки сегментов (`DATA SEGMENT`, `CODE SEGMENT`), линкеров (`TLINK`) и генерации тяжелых оверлеев. Это прошлый век.
- **Почему не NASM:** NASM хорош, но требует внешнего линкера для создания правильных DOS бинарников, либо сложных флагов командной строки.
- **Победа FASM:** Он идеально генерирует чистые `.COM` файлы (где код и данные живут в одном сегменте до 64 Кб) с помощью всего одной первой строчки: `org 100h`. Код получается плоским, предсказуемым, а сам компилятор FASM весит меньше мегабайта и работает мгновенно.

**2. Тестовая среда**

**DOSBox-X или DOSBox-Staging (на этапе разработки) + Итоговый тест в 86Box / QEMU.**

- **Для быстрой разработки:** Стандартный DOSBox удобен, но **DOSBox-X** или **DOSBox-Staging** точнее эмулируют тайминги процессора, работу прерываний мыши (`INT 33h`) и видеорежимы VGA. Мы сможем мгновенно перезапускать бинарник после сборки.
- **Для финальной валидации:** Чтобы убедиться, что интерпретатор строго держит лимит памяти и не падает на «железе», перед релизом его стоит прогнать в эмуляторе **86Box** (настроенном под IBM PC AT 286/386 с 640 Кб ОЗУ) или на чистом FreeDOS.

**3. Где писать код (VS Code vs DOS-редактор)?**

**Live-редактирование в современном редакторе (VS Code / Sublime) + Автосборка.**
Писать компилятор на ассемблере внутри DOS-редактора типа `edit.com` — это героический, но неэффективный мазохизм. У нас не будет удобного поиска, вкладок и подсветки синтаксиса.

**Идеальный воркфлоу настраивается за 5 минут:**

1. Мы пишем код ассемблера нашего интерпретатора в Intellij Idea.
2. Вешаем на горячую клавишу (или simple-скрипт) команду, которая вызывает Windows-версию `fasm.exe`.
3. FASM за 0.1 секунды собирает файл `yaz.com`.
4. Скрипт автоматически закидывает `yaz.com` в смонтированную папку DOSBox и выполняет его.



## Архитектурный каркас для старта в FASM

Чтобы мы могли сразу начать, вот как выглядит минимальный шаблон вашего будущего интерпретатора на FASM, который генерирует правильный `.COM` файл для DOS:

assembly

```
org 100h                ; Стартовая точка для всех DOS .COM программ

start:
    ; --- 1. ПРИВЕТСТВИЕ (Проверка работоспособности DOS) ---
    mov ah, 09h         ; Функция DOS: Вывод строки на экран
    mov dx, msg_hello   ; Адрес нашей строки
    int 21h             ; Вызов прерывания DOS

    ; --- 2. СЮДА МЫ НАПИШЕМ ГЛАВНЫЙ ЦИКЛ (REPL / ЧТЕНИЕ ФАЙЛА) ---
    ; Здесь будет ваш лексер, который читает суффиксы -sa, -ka и т.д.

exit_to_dos:
    mov ax, 4C00h       ; Функция DOS: Безопасный выход в консоль
    int 21h

; --- ДАННЫЕ И БУФЕРЫ (Все вместе поместится в 4 Кб) ---
msg_hello db 'Yaz Language Interpreter v0.1 loaded.', 13, 10, '$'

; Наш виртуальный стек для обработки суффиксов
virtual_stack:
    times 256 dw 0      ; Выделяем 512 байт под стек нашего языка
virtual_stack_top:      ; Указатель на вершину стека
```





# B. Память и лимиты

**1. Что входит в лимит 4 КБ?**

**Лимит 4 КБ должен покрывать ВЕСЬ `.COM` файл (Код интерпретатора + Системные буферы + Таблица токенов).**

- **Ядро компилятора:** Написанный на FASM код лексера, парсера и виртуальной машины займет около **1.5 – 2 КБ** [0x01, 0x02, 0x03].
- **Системные буферы:** Сюда входят стек виртуальной машины, буфер ввода строки и словарь токенов (еще около **1 КБ**).
- **Где живут данные пользователя:** Сама программа, которую пишет пользователь, и её переменные **НЕ входят** в эти 4 КБ. DOS при запуске `.COM` файла выделяет ему *полный сегмент памяти размером 64 КБ* (точнее, всё свободное ОЗУ до границ сегмента). Таким образом, у нас остается **60 КБ свободной памяти** для хранения кода пользователя, массивов и динамических строк.

**2. Количество переменных в первой версии**

**Рекомендуемый стандарт: 26 числовых (Твердых) + 26 строковых (Мягких).**

- Это классическая схема «Эллочки» и ранних версий BASIC, которая идеально экономит память.
- **Числовые (Твердые):** Переменные от `A` до `Z` (или `a` до `z` — парсер должен приводить их к одному регистру). Хранятся как массив из 26 слов (`dw`) по 2 байта каждое. Итого: всего **52 байта** в ОЗУ.
- **Строковые (Мягкие):** Переменные от `E` до `Z` (использующие только мягкие гласные, как мы проектировали). Чтобы не тратить память на 26 тяжелых буферов, мы храним массив из 26 **указателей** (адресов) на строки (`dw`). Сами строки выделяются динамически в свободной области ОЗУ (в хвосте 64 КБ сегмента). Итого: **52 байта** под указатели.

**3. Максимальная длина строки кода и литералов**

- **Максимальная длина строки исходного кода: 127 символов.**
  Это ограничение продиктовано встроенным прерыванием DOS `INT 21h / AH=0Ah` (системный буфер ввода). Функция DOS считывает максимум 127 символов, что идеально для построчного лексера. Буфер для чтения займет ровно **128 байт** в памяти интерпретатора. [[1](https://habr.com/ru/articles/141827/)]
- **Максимальная длина строкового литерала: 255 байт.**
  Длина строки (например, `"Привет, мир!"`) должна кодироваться **одним байтом**. Это позволяет виртуальной машине мгновенно прыгать через строки в памяти и эффективно выделять под них место.

Карта распределения 64 КБ сегмента DOS в памяти (Схема ОЗУ)

Когда ваш интерпретатор `yaz.com` загружается в DOS, память распределяется следующим образом:

```
[0x0100] ----------------------------------------------------

         |  КОД ИНТЕРПРЕТАТОРА (Ваш Ассемблер x86)           | ~2000 байт
         |  - Лексер суффиксов (-sa, -ka)                    |
         |  - Обработчики прерываний DOS                     |
         ----------------------------------------------------

         |  СИСТЕМНЫЕ БУФЕРЫ                                 | 
         |  - Буфер строки ввода (128 байт)                  | ~1000 байт
         |  - Таблица переменных (52 + 52 байта)             |
         |  - Виртуальный стек (512 байт)                    |
[0x1100] ---------------------------------------------------- <-- Конец 4 КБ лимита .COM файла

         |  СКОМПИЛИРОВАННЫЙ БАЙТ-КОД ПОЛЬЗОВАТЕЛЯ           |
         |  (Сюда токенизатор складывает байты программы)   | До 30-40 КБ
         ----------------------------------------------------

         |  ДИНАМИЧЕСКИЕ СТРОКИ И МАССИВЫ                    |
         |  (Сюда растут строковые переменные)               | До конца сегмента
[0xFFFF] ----------------------------------------------------
```

При такой структуре само ядро остается крошечным (помещается на сектор дискеты), но пользователь вашего языка никак не ограничен в размерах своих программ и может писать сложные GUI-приложения и вычисления.

# C. Грамматика первой версии

**1. Минимальный набор суффиксов для старта**

Ваше предложение — **идеальная инженерная стратегия**. Сначала нужно научить ядро обрабатывать 5 базовых атомарных суффиксов, а затем просто добавить в таблицу токенов их слитные комбинации.

**Стартовый набор первой версии:**

- `-sa / -se` (Условие, аналог `IF`)
- `-ka / -ke` (Направление/Вывод, аналог `PRINT/POKE`)
- `-dan / -den` (Исходный/Ввод, аналог `INPUT/PEEK`)
- `-ga / -ge` (Переход к цели, аналог `GOTO`)
- `-mas / -mes` (Отрицание, аналог `NOT`)

Как только этот базис заведется на ассемблере x86, добавление сложных токенов вроде `-masaga` или `-sadan` займет ровно 5 минут, потому что они будут собираться как битовые маски или последовательные вызовы базовых функций.

**2. Определение типа по гласным: ASCII-only или кодовые страницы?**

**Для первой версии — строго ASCII-only (A, O, U, Y против E, I).**

- **Почему это важно:** Стандартные шрифты BIOS / DOS на чистой латинице не содержат символов `ä`, `ö`, `ü`. Чтобы их отобразить, вам придется вручную перепрограммировать генератор знаков видеокарты VGA через регистры (`INT 10h, AX=1100h`) и подгружать растровые шрифты. Это сожрет около 1 КБ кода — четверть всего нашего лимита памяти!
- **Решение:** Мягкость в ASCII идеально кодируется буквами **E** и **I**. Например, переменная `data` (твердая, число), переменная `file` или `size` (мягкие, строки). Этого более чем достаточно для первой версии.

**3. Обозначение меток программ**

**Используем двоеточие в конце (`label:`), как в Эллочке и классическом Ассемблере.**

- **Плюс для парсера:** Когда лексер читает первое слово в строке, ему не нужно гадать, команда это или переменная. Если последний символ слова равен `:` (код `0x3A`), лексер мгновенно понимает: *«Это метка!»*. Он берет текущий адрес байт-кода и записывает его в таблицу переходов, очищая строку. Это самый дешевый по байтам способ реализации меток на ассемблере.

**4. Нужны ли комментарии в первой версии?**

**Да, комментарии жизненно необходимы, но они должны отсекаться «бесплатно» на этапе ввода.**

- Мы сделаем комментарии в стиле ассемблера — через точку с запятой `;` [0x01].
- **Реализация в 3 строчки кода:** Когда функция чтения строки с клавиатуры или диска (`INT 21h`) заполняет буфер, лексер бежит по символам. Как только он встречает `;`, он просто ставит на его место символ конца строки `0x0D` (или нуль-терминатор) [0x02].
- В итоге весь текст комментария мгновенно исчезает для компилятора, не занимает ни одного байта в ОЗУ программы и никак не усложняет грамматику.

------

**Архитектурный набросок лексера на FASM (Как отсечь комментарии и метки)**

Вот пример того, как лаконично на ассемблере x86 реализуется базовый разбор строки в цикле компилятора:

assembly

```
parse_line:
    mov si, buffer_input    ; SI указывает на начало введенной строки
.loop_chars:
    lodsb                   ; Читаем текущий символ в AL, SI двигается вперед
    cmp al, 13              ; Это конец строки (Enter)?
    je .done
    cmp al, ';'             ; Встретили комментарий?
    je .cut_comment
    cmp al, ':'             ; Встретили двоеточие (метка)?
    je .add_label
    
    ; ... тут продолжается логика чтения слов и суффиксов ...
    jmp .loop_chars

.cut_comment:
    dec si                  ; Шаг назад, на место ';'
    mov byte [si], 13       ; Искусственно завершаем строку прямо здесь
    jmp .done

.add_label:
    ; Логика сохранения адреса метки в таблицу переходов...
    jmp .done
.done:
    ret
```



# D. Компилятор vs интерпретатор (Обновлённый манифест)

**1. Делаем ли мы только интерпретатор на первом этапе?**
**Нет, мы делаем ОДНОВРЕМЕННО и интерпретатор, и компилятор в одном `.COM`-файле прямо на первом этапе.**

- **Как это устроено:** Мы создаём **интерактивную среду компиляции (Interactive Compiler)** в стиле Forth-систем. Лексер строк и генератор машинного x86-кода у интерпретатора и компилятора **общие**.
- **Как работает интерпретатор (REPL):** Мы вводим строку кода в консоли DOS, движок *на лету* компилирует её в машинные байты x86 во временный буфер ОЗУ, процессор выполняет этот буфер через `CALL`, а затем буфер очищается. Для меня это выглядит как мгновенная интерпретация.
- **Как работает компилятор:** Тот же самый движок переключается в режим чтения файла `.alf`, генерирует точно такой же нативный машинный код x86, но последовательно записывает его в новый исполняемый `.COM`-файл на флоппи-диск.

------

**2. Компилятор будет делать AOT в отдельный .COM или саморазворачивающийся скрипт?**
**Компилятор делает чистый Ahead-of-Time (AOT) компилированный нативный `.COM`-файл.** 

- Никаких «саморазворачивающихся скриптов» с пришитым байт-кодом и тяжёлым рантаймом. На выходе получается независимый, «чистокровный» бинарник DOS, состоящий исключительно из машинных команд процессора Intel 8086 (`MOV`, `CMP`, `JE/JNE` и прерываний `INT`).
- Наш синтаксис (Способ со слитными суффиксами и сингармонизмом) избавлен от скобок и сложных выражений, поэтому он транслируется в машинный код линейно, один в один. Скомпилированная пользовательская программа будет весить всего от **20 до 100 байт** и работать со скоростью процессора, а сам компилятор-интерпретатор легко удержится в рамках **4 КБ**.



# E. Тестирование и совместимость (Итоговый манифест)

**1. Как проверяем корректность?**
**Мы пишем эталонные файлы-тесты (скрипты) на самом языке и прогоняем их через DOSBox.**

- Поскольку компилятор и интерпретатор теперь объединены в одно целое на ассемблере x86, мы не можем сделать встроенную тестовую систему, как в Zig (это раздуло бы `.COM`-файл).
- **Как делаем:** Мы создадим 5–10 эталонных тестовых файлов (например, `test_math.alf`, `test_cond.alf`). Каждый тест будет проверять конкретную группу суффиксов (`-sa`, `-ka`, `-masaga` и т.д.). Результат теста (например, вывод чисел на экран) должен строго совпадать с эталоном. Проверка работоспособности будет выглядеть как запуск батника в DOSBox: `yaz.com test_math.alf`.

**2. Нужна ли на первом этапе обратная связь по ошибкам?**
**Да, нужна, но в ультра-компактном формате «Кодов Ошибок» (Micro-Diagnostic Codes), чтобы уложиться в 4 КБ.**

- Хранение длинных текстовых строк вроде `Error: Suffix mismatch for this type` быстро сожрёт драгоценные байты в DOS.
- **Как делаем:** Мы создадим систему из 4–5 числовых кодов ошибок. При их возникновении компилятор-интерпретатор будет прерывать работу и выводить в консоль лаконичное сообщение, например: `ERR 1` или `ERR 2`.

Карта микро-ошибок (Diagnostic Map) для ядра:

| Код ошибки | Системное имя в FASM | Что означает для программиста                       | Из-за чего возникает в коде                                  |
| ---------- | -------------------- | --------------------------------------------------- | ------------------------------------------------------------ |
| **ERR 1**  | `err_harmony`        | **Сбой сингармонизма** (Vowel/Type Mismatch)        | Попытка применить твердый суффикс к мягкому слову (или наоборот). Например, `file -sa`. |
| **ERR 2**  | `err_token`          | **Неизвестное слово/суффикс** (Unknown Token)       | Лексер не смог найти корень слова или суффикс в системном словаре. |
| **ERR 3**  | `err_stack`          | **Переполнение стека** (Stack Overflow / Underflow) | Математические операции или суффиксы вызова функций нарушили баланс стека. |
| **ERR 4**  | `err_label`          | **Метка не найдена** (Label Not Found)              | Суффикс перехода (например, `-saga`) ссылается на метку, которой нет в программе. |

Как это реализуется на ассемблере FASM:

Внутри кода вашего компилятора под каждую ошибку выделяется всего одна строчка. Вся процедура вывода ошибок займет не более 40 байт:

assembly

```
; Функция вывода ошибки. Номер ошибки передается в регистре AL (например, '1', '2'...)
print_error:
    mov [err_code_char], al    ; Вставляем символ номера ошибки в строку
    mov ah, 09h                ; Функция DOS: Печать строки
    mov dx, msg_err            ; Адрес строки 'ERR X'
    int 21h
    mov ax, 4C01h              ; Аварийный выход в DOS с кодом 1
    int 21h

msg_err db 'ERR '
err_code_char db '0', 13, 10, '$'
```

Такой подход гарантирует, что вы никогда не запутаетесь при отладке своих программ, но при этом ядро компилятора сохранит абсолютную диетическую легкость для дискеты.

-----

Backpatching (заплатки) — оптимальное решение для потокового JIT в 4 КБ DOS-памяти, обеспечивающее поддержку forward-labels как в REPL, так и AOT-режимах без необходимости двухпроходной компиляции. Метод заключается в записи заглушки (fixup) в коде при обнаружении перехода вперед, которая впоследствии обновляется, когда компилятор достигает целевой метки. Эта методика позволяет эффективно реализовывать условные переходы, оставляя код минимальным и компактным.

**1. Разрядность сравнений и диапазон чисел**

- **Решение по разрядности:** **Везде используем 16-битные регистры (`AX`, `BX`) для чисел.**
  Так как наши переменные определены как `dw` (16 бит), использовать 8-битные регистры небезопасно (можно потерять старший байт). Исключение — низкоуровневые операции ввода-вывода (чтение порта `IN AL, DX` или считывание символа клавиатуры `INT 16h`), но даже после них мы будем расширять результат до 16 бит (`XOR AH, AH`), чтобы вся дальнейшая математика и сравнения шли единообразно через `AX/BX`. Это сильно сократит код самого компилятора.
- **Диапазон чисел:** **Строго знаковые (`-32768..32767`).**
  Для прикладных программ (возраст, баланс, счетчики циклов, температура) знаковые числа интуитивно понятны. На уровне ассемблера x86 для условных суффиксов (`-sa_kise` / меньше, и т.д.) мы будем использовать инструкции **`JG/JL` (Jump if Greater/Less)** вместо беззнаковых `JA/JB`.

------

**2. Формат вызова и выходной файл**

- **Имя выходного файла:** **То же имя + расширение `.com`.**
  Если компилятор получает `main.alf`, на выходе автоматически генерируется `main.com`. Это классическое поведение большинства DOS-компиляторов. Избавляет от необходимости парсить сложные аргументы командной строки в 4 КБ.
- **Формат вызова:** **Один бинарник, флаг `/c` для компиляции.**
  - `alifba.com main.alf` → запуск файла в режиме интерпретации.
  - `alifba.com /c main.alf` → компиляция файла в `main.com`.
    Такой подход делает утилиту невероятно удобной и монолитной.

**3. Переполнение стека и сложность арифметики**

- **Арифметика в v0.1:** **Только плоские присваивания и сравнения.**
  Никаких сложных выражений со скобками вроде `(a+b)*c`. В первой версии выражение может содержать только одну операцию или константу. 

- **Нужен ли вычислительный стек?** **В v0.1 отдельный стек вычислений НЕ нужен.**
  Поскольку грамматика плоская, все вычисления компилятор может делать напрямую через регистры `AX` и `BX`. Ошибка `ERR 3` (Stack Overflow) резервируется **исключительно под стек вызовов процедур** (когда через суффикс `-ge` одна функция вызывает другую, и адрес возврата `IP` кладется в системный стек процессора x86). Если пользователь сделает слишком много вложенных вызовов (например, бесконечную рекурсию), сработает `ERR 3`.

  

**4. Судьба REPL в версии v0.1**

- **Решение:** **Начинаем строго с файлового режима, REPL откладываем на следующую версию.**
  Это самое мудрое решение для снижения рисков на старте. Интерактивный ввод с клавиатуры тянет за собой сложную эхо-печать, обработку клавиши Backspace, управление курсором DOS и мгновенный JIT-вызов памяти. Файловый режим (`alifba.com test.alf`) позволит нам сфокусироваться на главном: идеальной работе лексера, валидации сингармонизма, бэкпэтчинге меток и генерации чистого машинного кода.
